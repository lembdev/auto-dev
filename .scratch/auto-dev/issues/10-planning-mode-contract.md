# Режим планирования: ход сессии и контракт выхода (milestones, issues, зависимости, labels)

Type: grilling
Status: resolved
Blocked by: 06

## Question

Как проходит сессия планирования: сессия Claude Code на ветке main, чат в UI, какой промпт и какие skills (grilling?). Когда планирование считается завершённым и кто это решает. Что именно создаётся в GitHub: milestones, issues с телом по шаблону, нативные зависимости, sub-issues, labels из словаря тикета 06. Можно ли дополнять план поверх существующего (вторая сессия планирования). Как планировщик учитывает уже существующий код в репо.

## Notes

- Из research 03: зависимости через `gh issue create --blocked-by`, до 50 на issue; sub-issues до 100 на родителя; sub-issue того же владельца.
- Из тикета 06: планировщик ставит на каждую созданную issue метку `auto-dev:queued` (это и opt-in, и очередь); порядок взятия: milestone по дате/номеру, затем номер issue; приоритетных меток нет, приоритет через зависимости и milestone.
- Референс Breedly/breedly-ios (ADR-0024, docs/agents/issue-tracker.md): milestone = эпик, в нём зонтик типа Epic, спека типа Spec, работа Task/Bug подзадачами зонтика; агент берёт только Task/Bug с `ready-for-agent`; каждая веха заканчивается одной задачей приёмки с меткой `check:acceptance`, без блокеров, берётся последней по рангу; порядок вех = порядок заведения, тикет без вехи берётся последним; один тикет = один экран или одно поведение, потолок ~600 добавленных строк. Постановка задач идёт через /wayfinder, /to-spec, /to-tickets (mattpocock/skills) с GitHub-трекером. Оговорка: issue types есть только в org, в личном lembdev/auto-dev их нет (research 03), значит тип выражать label (`type:epic|spec|task|bug`) или родителем.
- Фактический контракт breedly-api (`docs/agents/issue-tracker.md`): тело Task = разделы Parent (`#<epic> (спека #<spec>)`), What to build, Acceptance criteria чек-листом, Blocked by; Epic хранит «Критерии закрытия» чек-листом, и закрывающий критерий Task обязан отметить его в Epic при закрытии; отдельной задачи приёмки нет, milestone закрыт, когда закрыты все тикеты и отмечены все критерии. Планировщик auto-dev должен выдавать ровно этот формат, а Merger при закрытии Задачи отмечать критерии в Epic.

## Answer

Решено 2026-11-05 (рекомендации агента, принятые пользователем заранее).

1. **Сессия планирования** = обычная Сессия через тот же Драйвер, роль «Планировщик», cwd = клон Продукта на `main` (не worktree). Планировщик ничего не коммитит: результат только в GitHub Issues. Одновременно не больше одного Планировщика на Установку; Слот Конвейера он не занимает.
2. **Промпт и skills.** Системный промпт auto-dev + skills mattpocock `/wayfinder`, `/to-spec`, `/to-tickets` и контракт трекера Продукта `docs/agents/issue-tracker.md` (он главный: формат берётся оттуда, не из auto-dev). Перед созданием задач Планировщик обязан прочитать `GLOSSARY.md`, `docs/adr/`, структуру репо. UI Режима планирования = тот же компонент чата, что карточка Агента (09), без поля Запроса: Планировщик спрашивает прямо в чате, ask_human ему не нужен.
3. **Что создаётся** (контракт breedly-api): milestone `Эпик N: <тема>`; Epic с целью, границами и «Критерии закрытия» чек-листом; Spec; Task/Bug как sub-issues Epic с телом Parent / What to build / Acceptance criteria / Blocked by; нативные blocked_by; `ready-for-agent` на Task/Bug. Типы issue: org-типы, где есть; в личном репо без типов Оркестратор считает Задачей любой open issue с `ready-for-agent` (Epic и Spec метку не получают никогда).
4. **Завершение** решает человек: кнопка «Завершить планирование» в UI гасит процесс. Автокритериев нет. Сессия сохраняется: следующий заход в Режим планирования предлагает «продолжить прошлую» (resume) или «новую».
5. **Дополнение плана.** Планировщик всегда сначала читает открытые milestones и issues и добавляет к ним; пересоздание запрещено промптом; правка существующих issue только по явной просьбе человека.
6. **Старт работы.** Оркестратор берёт Задачи сразу, как они получили `ready-for-agent` и остались без блокеров; отдельной кнопки «запустить план» нет. Сдерживать взятие можно тумблером «Пауза» (тикет 12).

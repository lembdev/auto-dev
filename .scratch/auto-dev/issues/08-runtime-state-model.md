# Модель рантайм-состояния на VM и восстановление после рестарта

Type: grilling
Status: resolved
Blocked by: 05

## Question

Что именно хранится локально (индекс: задача -> стадия -> session id -> процесс -> worktree -> PR -> круг QA), в каком формате (SQLite, JSON-файлы), как оркестратор при старте сверяет индекс с GitHub и живыми процессами, что делает с незавершёнными стадиями (продолжить сессию или начать заново). Транскрипт не хранится: UI читает родные файлы сессий Claude Code.

## Notes

- Из research 02: хранить session_id и путь к JSONL; для истории SDK-сессий есть `sessionStore` (listSessions, getSessionMessages).
- Из тикета 05: идентичность Агента = session id, процесс взаимозаменяем; рестарт оркестратора = `resume` всех живых Агентов с `CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1`; индекс должен хранить session id, idle-таймер и last-known-good `claude --version`.
- Из research 05 (Codeman): раскладка worktree `<repo>/.claude/worktrees/<name>`, ветка `worktree-<name>`, имена `[A-Za-z0-9._-]` до 64, совпадает с нативным `claude --worktree`; использовать её (или опцию worktree SDK), `.claude/worktrees` в git exclude. В Рантайм-индексе хранить также применённые `(clientId, seq)` и id комментариев GitHub для дедупа Ответов.
- Решение по 06 (2026-11-05): стадия Конвейера хранится только здесь, в GitHub меток auto-dev нет. Значит Рантайм-индекс обязан быть восстановимым и единственным источником стадии: при рестарте Оркестратора стадия читается из индекса, а не выводится из GitHub; сверка с GitHub только по assignee, `ready-for-agent`, состоянию issue и PR.
- Решение по 07 (2026-11-05): индекс хранит открытый Запрос к человеку (session id, id вызова tool, id комментария-Запроса, время публикации) и применённые Ответы (id комментария GitHub, `clientId`+`seq` из UI). После рестарта Оркестратор продолжает ждать и опрашивает комментарии с `since` = время Запроса.

## Answer

Решено 2026-11-05 (grilling; пользователь принял рекомендации без правок).

1. **Формат и место.** Один файл SQLite через `node:sqlite` (Node 22+), без ORM: `/var/lib/auto-dev/runtime.db`. Клон Продукта `/var/lib/auto-dev/repo`, worktree внутри него `.claude/worktrees/<имя>` (раскладка `claude --worktree`, каталог в git exclude). В индекс пишет только Оркестратор; UI читает через его API, не из файла. Версия схемы в таблице `installation`, миграции только вперёд.
2. **Таблицы.** `tasks` (issue, milestone, стадия, круг QA, PR, ветка, путь worktree, время взятия); `agents` (задача, роль, session id, состояние процесса: работает / idle / ждёт / остановлен, PID, время последнего Хода); `human_requests` (открытый Запрос: агент, id вызова tool, id комментария, время); `applied_answers` (id комментария GitHub или `clientId`+`seq` из UI); `pending_messages` (очередь недоставленных сообщений Диалога); `installation` (last-known-good `claude --version`, курсоры опроса GitHub `since` и ETag, версия схемы); `transitions` (история переходов стадий с временем, источник «истории задач» для UI).
3. **Чего нет.** Транскриптов (их отдаёт `sessionStore` SDK), потока событий Агента (live-стрим в UI, история из `sessionStore`), текстов Запросов и Ответов (они в GitHub, в индексе только id).
4. **Старт: процессы.** Все PID из `agents` считаются сиротами: SIGTERM, пауза, SIGKILL. Затем каждый Агент не в Ожидании поднимается `resume` с `CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1`. Ждущие не поднимаются до Ответа.
5. **Старт: сверка с GitHub.** На каждую задачу из `tasks` один запрос issue и PR. Issue закрыта без влитого PR = Отмена; PR влит = завершение; сбитые человеком assignee или `ready-for-agent` восстанавливаются по индексу. Стадия берётся только из индекса, из GitHub не выводится.
6. **Незавершённая Стадия.** Всегда продолжение Сессии, никогда заново; QA посреди Круга тоже resume. Три подряд провала resume = тупик (`ready-for-human`, как в 06).
7. **Краш между индексом и GitHub.** Внешнее действие (ветка, worktree, PR, комментарий) сначала записывается в индекс как намерение, затем выполняется, затем отмечается сделанным. На старте незавершённые намерения досовершаются идемпотентно: проверить существование PR для ветки, worktree, комментария с маркером, второй не создавать.

Последствия для карты: фог «жизненный цикл worktree и ресурсов» стал тикетом 19; из фога «наблюдаемость» ушла «история задач» (таблица `transitions`); заметки в 09, 12, 13.

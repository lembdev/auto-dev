# Жизненный цикл задачи и словарь labels в GitHub

Type: grilling
Status: resolved
Blocked by: 03

## Question

Как состояние задачи отражается в GitHub? Какая issue считается «готовой к взятию» (label, отсутствие открытых блокеров, порядок milestone, приоритет)? Какие labels/статусы для стадий (взята, реализация, QA, merge, ждёт человека, готово, провалена)? Кто их ставит (только оркестратор). Как закрывается issue и milestone. Что делать с issue, созданными человеком вручную без планировщика.

## Notes

- Из research 03: готовность = open && `issue_dependencies_summary.blocked_by == 0`; issue types недоступны (личный репо), только labels; milestone закрыт когда `open_issues == 0` (PR могут считаться, не подтверждено); secondary limits: записи последовательно, 1 с между ними.

## Answer

Решено 2026-11-04 (grilling; последние пункты по рекомендации, пользователь попросил не спрашивать дальше).

Простыми словами: вся правда о задаче живёт в одной метке GitHub вида `auto-dev:<статус>`. Ровно одна метка на задачу. Нет метки - оркестратор issue не видит.

1. **Какие issue берутся в работу.** Только issue с меткой `auto-dev:queued`. Её ставит планировщик, или человек руками на любую свою issue. Остальные issue репозитория оркестратор не трогает и не читает.
2. **Семья меток, ровно одна на задаче:** `auto-dev:queued` (в очереди), `auto-dev:implementing` (пишется код), `auto-dev:qa` (проверка), `auto-dev:merging` (вливается), `auto-dev:waiting` (ждёт ответа человека), `auto-dev:failed` (оркестратор не смог продолжить). Пока задача ждёт человека, стадия видна только в локальном индексе и в комментарии-вопросе; после ответа метка возвращается на стадию.
3. **Готова к взятию** = метка `queued` + issue открыта + у неё нет открытых блокеров (поле `issue_dependencies_summary.blocked_by == 0`, нативные зависимости GitHub). Если блокер - обычная issue без метки, задача ждёт, пока человек её закроет.
4. **Порядок взятия:** сначала задачи самого раннего открытого milestone (по дате, без даты - по номеру milestone), задачи без milestone последними; внутри - по номеру issue. Меток приоритета нет: приоритет выражают зависимости и milestone.
5. **Метки ставит только оркестратор** (кроме первой `queued`). Любое расхождение метки с локальным индексом оркестратор при опросе молча восстанавливает. Снять метку руками можно только у `queued`; у задачи в работе снятие ничего не значит.
6. **failed** - только технический тупик: сессия не возобновляется после нескольких попыток, пропали worktree или ветка, человек закрыл PR без merge. Всё содержательное (не понимает, не проходит QA после всех кругов, конфликт) идёт в `waiting`. Выход из failed: человек снова ставит `queued`, оркестратор стартует с чистой сессии и нового worktree, старый PR закрывается.
7. **Закрытие issue:** оркестратор пишет `Closes #N` в тело PR, GitHub закрывает issue в момент merge в main. Оркестратор при опросе видит merged PR и закрытую issue, снимает метку `auto-dev:*` и чистит рантайм. Закрытая задача без метки. Работает и если человек влил PR руками.
8. **Отмена человеком:** issue закрыта руками без merged PR = отмена. Оркестратор гасит агента, закрывает PR, снимает метку, чистит рантайм. Отменить или приостановить задачу в работе можно только закрытием issue или из UI. Отдельной метки paused нет.
9. **Повторное открытие** закрытой issue ничего не запускает: метки нет, значит не задача. Хочешь переделать - ставь `queued` заново, старт с чистой сессии.
10. **Milestone закрывает оркестратор**, когда у него `open_issues == 0`, при очередном опросе. Проверка только по milestone, где была хоть одна задача оркестратора.
11. **Issue, созданные руками:** шаблона тела нет. Реализатор работает с тем, что есть; если непонятно - задаёт вопрос через ask_human.
12. **Метки создаёт оркестратор** при старте, идемпотентно (имя, цвет, описание), если их нет в репозитории.

Что это меняет на карте: разблокированы 10 (планирование) и 11 (merge). В 11 уже зафиксировано: `Closes #N` в теле PR, закрытие milestone оркестратором. Фог «жизненный цикл worktree» дополнился сценарием отмены и повторного `queued`.

## Comments
- 2026-11-05: фактический Продукт Breedly/breedly-api уже размечен иначе: opt-in = `ready-for-agent` (ставит /to-tickets), тип Task/Bug = org issue type, родитель Epic через sub-issue, порядок = milestone по дате заведения, затем номер; `check:acceptance` снята из конвенции. Предложение к пересмотру: `ready-for-agent` остаётся opt-in и снимается Оркестратором при взятии; `auto-dev:<статус>` только для implementing/qa/merging/waiting/failed; `queued` не нужен (= `ready-for-agent` без `auto-dev:*`); failed = `ready-for-human` + `auto-dev:failed`. Готовность = open + Task/Bug + `ready-for-agent` + нет `auto-dev:*` + нет открытых blocked_by + нет assignee.

## Answer (пересмотр 2026-11-05)

Решение пользователя: словарь меток и структура milestone берутся из Продукта Breedly/breedly-api как есть (`docs/agents/issue-tracker.md` там). Прежний ответ действует в части, не противоречащей этому.

- Структура: milestone = эпик (`Эпик N: <тема>`), в нём Epic (зонтик с критериями закрытия чек-листом), Spec, Task/Bug подзадачами Epic (или мини-спеки). Типы issue org-уровня: Оркестратор берёт только Task и Bug. Блокировки нативные (blocked_by). Отдельной задачи приёмки нет; `check:acceptance` игнорировать, метка добавлена по ошибке и снимается.
- Opt-in = `ready-for-agent` (ставит человек или /to-tickets). Метки `auto-dev:queued` нет: очередь = open + Task/Bug + `ready-for-agent` + нет открытых blocked_by + нет assignee.
- Порядок взятия: milestone по порядку заведения, внутри по номеру; без milestone последним.
- Решение пользователя 2026-11-05: своих меток auto-dev в GitHub не заводит вовсе. Стадия Конвейера (implementing / qa / merging / waiting / failed) живёт только в Рантайм-индексе и показывается в UI. В GitHub взятие Задачи видно по assignee (Оркестратор назначает себя) и снятому `ready-for-agent`; Ожидание видно по комментарию с Запросом к человеку.
- Завершение: PR влит, issue закрыта через `Closes #N`, критерии закрытия Epic, покрытые Задачей, отмечены. Milestone закрывает Оркестратор, когда закрыты все issues вехи и отмечены все критерии Epic; тогда же закрываются Epic и Spec.
- Тупик (исчерпаны Круги QA или технический сбой): ставится `ready-for-human`, assignee снимается, причина комментарием. Возврат в очередь = человек снова ставит `ready-for-agent`.
- Отмена: issue закрыта руками без влитого PR, как раньше.
- Триаж-роли `needs-triage` / `needs-info` / `wontfix` Оркестратор не трогает и такие issue не берёт.

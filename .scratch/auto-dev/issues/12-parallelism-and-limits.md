# Параллелизм и поведение при исчерпании лимита подписки

Type: grilling
Status: resolved
Blocked by: 01

## Question

Сколько задач ведётся одновременно (настройка, значение по умолчанию), как считается слот (ждущий агент слот не держит), есть ли приоритеты между milestones. Что делает оркестратор при достижении лимита Max (пауза всех агентов до сброса окна, как это детектировать, как показывается в UI). Как показывается расход лимита.

## Notes

- Из research 01: капа на concurrent sessions не найдено; исчерпание видно в stream-json `rate_limit_event` (status, resetsAt, utilization); остаток только через JSON statusline `rate_limits`; `CLAUDE_CODE_RETRY_WATCHDOG=1`.
- Из research 05 (Codeman): `rate_limits` в statusline: `used_percentage` целые 0-100, `resets_at` в epoch секундах, нет на первом рендере, подтверждено на 2.1.177 с Max; лимит общий на аккаунт, значит один индикатор на Установку; пороги подсветки 60/85%; statusline, если нужен, инжектить только в настройки процесса Агента, не в файлы Продукта. У стены: не стартовать новые Ходы до `resetsAt` + 2 мин, живые Сессии не трогать, ретрай 5 мин при повторном отказе; пре-арм по процентам (не стартовать Ход при >= 95%) как опция. Сначала проверить, даёт ли `rate_limit_event` SDK utilization без rejected, тогда statusline не нужен.
- Решение по 08 (2026-11-05): занятые Слоты считаются по таблице `agents` (состояние «работает» или «idle»; «ждёт» и «остановлен» Слот не держат); ограничение параллелизма и состояние «у стены» хранить в `installation`.

## Answer

Решено 2026-11-05 (рекомендации агента, принятые пользователем заранее).

1. **Слоты.** Настройка `max_parallel_tasks`, default 2. Слот занят Задачей, чей Агент «работает» или «idle»; Ожидание и «остановлен» Слот не держат. Планировщик вне Слотов.
2. **Порядок** как в 06: milestone по порядку заведения, внутри по номеру; приоритетов нет. Задачи одного milestone идут параллельно.
3. **Тумблер «Пауза»** в UI: новые Задачи и новые Круги QA не стартуют, живые Ходы дорабатываются. Состояние в `installation`.
4. **У стены (лимит Max).** Детект: `rate_limit_event` со `status: rejected` или `result.is_error` с текстом лимита. Установка переходит в «у стены» до `resetsAt` + 2 мин: новые Ходы не стартуют, живые процессы гасятся как idle, Ответы копятся в `pending_messages`. По истечении - resume всех прерванных Ходов (`CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1`). Повторный отказ сразу после сброса = ретрай через 5 мин. Задачи не помечаются, в GitHub ничего не пишется.
5. **Расход лимита.** Источник 1: `rate_limit_info.utilization` из `rate_limit_event`, если приходит без `rejected`. Источник 2 (если 1 не даёт данных): statusline-команда, инжектируемая в настройки процесса Агента (не в файлы Продукта), пишет `rate_limits` в файл Установки, Оркестратор читает. Последнее значение в `installation`. Один индикатор на Установку: `five_hour` и `seven_day` в процентах и время сброса; подсветка 60 / 85 %.
6. **Пре-арм:** при `five_hour >= 95 %` новые Ходы не стартуют (опция, default включено).
